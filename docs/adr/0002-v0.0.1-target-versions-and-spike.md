## スパイク手順

`scripts/spike-server.sh` で、隔離フォルダー（`local/spike-server`）に Fabric 専用サーバー、Fabric API、Geyser-Fabric、Hydraulic、fixture MOD を配置した。Geyser の起動完了行（`Run /geyser help`）を確かめてから stop で停止した。サーバー設定は `online-mode=false`、`server-ip=127.0.0.1` で、新規ワールドを作成した。

### 分かったこと・既知の制約

1. **Geyser 2.12 の既定トランスポートは NetherNet**（WebRTC とシグナリング）であり、RakNet ではない。従来の「IP とポートを指定して接続」に合わせるため、スクリプトは 2 回目以降の起動で `transport: both`（RakNet は UDP 19132、NetherNet は UDP 19133）にする。待受を `127.0.0.1` にすると、Geyser は「NetherNet は loopback では動かず、全員タイムアウトする」と警告する。実機で確認するときは `--keep-running`（待受 `0.0.0.0`）を使い、同じ PC 上のクライアントでも LAN アドレスに接続する。
2. Geyser の初期設定では、**起動時に公開 STUN サーバー**（Cloudflare、Google）へ問い合わせ、ログに公開 IP を書き出す。スクリプトでは 2 回目以降の起動で `stun-discovery: false` にし、ログの保存時と表示時に IP を伏せ字にしている。ログはコミットしない。
3. **Floodgate の Fabric 版**は GeyserMC Downloads API に無い（spigot / bungee / velocity だけ）。v0.0.1 では `online-mode=false` で認証を省いて確認した。Floodgate 認証は #5 で、Modrinth の配布物を固定して検証する。
4. Windows で生成した `.mcpack` は、ZIP 内のパス区切りが `\`（例 `models\blocks\test_block.json`）になっている。ZIP の仕様ではパス区切りは `/` なので、Bedrock クライアントがこのパスを解決できるかは未確認。実機確認での最重要の観察点で、問題があれば Hydraulic へ報告する。Linux サーバーなら発生しない見込み（未確認）。
5. Hydraulic は Mixin の対象として任意依存のクラス（`de.ambertation.wover…`）を参照し、読込時に `ClassNotFoundException` の WARN を 1 件出す。起動は継続するので、今のところ実害はない。
6. JDK 26 では、Gson による final フィールドの書き換えと `sun.misc.Unsafe` の使用について WARNING が出る。いずれも上流の依存ライブラリが原因で、本プロジェクトのコードではない。
7. stdin の名前付きパイプは Git Bash 上の Windows ネイティブプロセスに届かない（`IOException: ハンドルが無効です`）。stop コマンドは通常のパイプで送る方式にした。
8. 起動途中に送った `stop` はコマンドエラーになり、サーバーは止まらない。また Git Bash の `kill` は Windows の java に届かない。そのためスクリプトは、起動完了後にだけ stop を送る。失敗時は、`-Dmodbridge.spike=<時刻>` を付けた、その回の java だけを `jps` で特定し、OS の PID で強制終了する。
9. fixture のブロックは `requiresCorrectToolForDrops()` 付きのため、`minecraft:mineable/pickaxe` タグに登録してツルハシで壊したときだけドロップするようにした。素手で壊してドロップしないのは仕様どおり。

## Bedrock 実機での確認手順（owner 向け・未実施）

1. 自動停止モードで 1 回以上起動して Geyser 設定を生成し、`MODBRIDGE_ACCEPT_EULA=true scripts/spike-server.sh --keep-running` を実行する（LAN 全体に公開されるため、信頼できる LAN でだけ使う）。
2. 純正 Bedrock クライアント（同じ LAN）で「サーバーを追加」を選び、サーバーの LAN アドレスとポート 19132 を指定して接続する（RakNet）。つながらない場合は、LAN の「フレンド」タブにサーバーが出るかも確認する（NetherNet）。
3. 次の点を確認して記録する。必須リソースパックの配布、ログイン、`/give @s pmb_fixture:test_ingot`（Java 側のコンソールで実行）の表示とテクスチャ、`pmb_fixture:test_block` の設置・ツルハシでの破壊とドロップ、名称（ja_JP）、切断後の再接続。
4. 接続できなかった場合は、クライアント側のエラー表示とサーバーログの該当部分を記録する。そのうえで、このADRに代替案（NetherNet だけでの接続、Linux 上での `.mcpack` 生成、Hydraulic へのパッチ）を追記する。

## 判断

- Mode A は **Geyser + Hydraulic の公開拡張点（MOD 読込時の自動変換と、Geyser のカスタムアイテム・ブロック登録）を前提に進める**。サーバー側の成立は実測で確認した。登録は Java 側の MOD 初期化で確定し、Geyser 側の登録はサーバー起動後かつ Bedrock 接続の受付前に行われる。そのため #5 の「接続前の定義登録」はこの順序に合わせて設計する。
- 実機接続の結果次第で、この判断を見直す。未成立の場合は、上の代替案を ADR に追記し、#5 の前提を修正する。
